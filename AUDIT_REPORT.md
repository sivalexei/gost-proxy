# Отчёт: сборка, тестирование и аудит gost-proxy

Дата: 2026-08-01
Окружение: Linux x86-64 (ALT Linux, ядро 6.18), gcc, nasm 2.x, CPU с AVX2/AES
Проверенные состояния кода: `HEAD` (d8cfe40) и текущий рабочий каталог (3 незакоммиченных файла)

---

## 1. Резюме

Проект **не собирается** в текущем состоянии и **не работает** ни в одном из двух
проверенных состояний. Обнаружено 5 независимых блокирующих дефектов, каждого из
которых по отдельности достаточно, чтобы туннель не передавал данные, и 6
критических проблем безопасности, включая полное отсутствие аутентификации и
воспроизводимое повторное использование гаммы.

| Проверка | HEAD | Рабочий каталог |
|---|---|---|
| `make` | собирается | **ошибка компоновки** (дублирование символа) |
| `make test` | **ошибка компоновки** | собирается, **SIGSEGV** |
| Крипто-тесты RFC 7801 (ASM) | **зависание** (бесконечный цикл) | **SIGSEGV** |
| Крипто-тесты RFC 7801 (C-реализация) | **все 5 пройдены** | **4 из 5 провалены** |
| Запуск сервера | **зависание на 100% CPU** | не проверялся (не собирается) |
| SOCKS5 end-to-end (curl) | — | **отказ**, туннель данные не передаёт |

Единственный корректный компонент — **C-реализация «Кузнечика» из HEAD**: она
полностью соответствует RFC 7801. Всё остальное в криптослое сломано.

## 2. Сборка

### 2.1. Рабочий каталог — ошибка компоновки

```
ld: build/kuznyechik.o: повторное определение «kuznyechik_precompute_tables»;
    build/gost_cipher.o: здесь первое определение
make: *** [Makefile:65: build/gost-server] Error 1
```

Функция `kuznyechik_precompute_tables` определена одновременно в
`src/crypto/gost_cipher.c:126` и в `src/crypto/kuznyechik.asm:999`.

### 2.2. HEAD — `make test` не компонуется

В `Makefile` цели `gost-test` не хватало `$(KUZ_OBJ)`, а `gost_cipher.c` публичный
API не экспортирует (все функции `static`):

```
undefined reference to `kuznyechik_set_key'
undefined reference to `kuznyechik_encrypt_ctr'   (и ещё 7)
```

То есть на HEAD команда `make test` из README никогда не работала.
В рабочем каталоге это уже исправлено, но появилась ошибка из п. 2.1.

### 2.3. Предупреждения nasm — испорченные таблицы

Сотни повторяющихся предупреждений:

```
src/crypto/kuznyechik.asm:977: warning: byte data exceeds bounds [-w+number-overflow]
```

Причина — директива `db` с 16-битными значениями:

```asm
db 0x6A60, 0x6A60, 0x6A60, ...   ; каждое значение обрезается до 0x60
```

Таблицы `L_table` / `InvL_table` заполнены обрезанным мусором.

### 2.4. Непереносимая конфигурация сборки

`Makefile:3-4`:

```make
CFLAGS  = ... -I /tmp/msquic-full/src/inc
LDFLAGS = -lpthread -lmsquic
```

* путь `/tmp/msquic-full` захардкожен — сборка на чистой машине невозможна;
* `grep -rn 'msquic\|MsQuic\|QUIC_API' src/` не даёт **ни одного совпадения** —
  библиотека линкуется, но не используется. «QUIC-слой» (`quic_layer.c`) —
  это обычный UDP через `sendto`/`recvfrom`/`poll`;
* `rpmbuild/SPECS/gost-proxy.spec`: в `BuildRequires` нет `nasm` (и msquic),
  хотя сборка их требует.

## 3. Криптография

### 3.1. Ассемблерная реализация на HEAD — `;` как разделитель инструкций

В nasm точка с запятой начинает **комментарий**, а не отделяет инструкции. Код
написан в предположении обратного:

```asm
kuznyechik_set_key:
    push rbp; mov rbp,rsp          ; ← "mov rbp,rsp" отброшен как комментарий
    movdqu xmm0,[rdi]; movdqu [rsp+16],xmm0   ; ← сохранение отброшено
key_groups:
    cmp r10d,4; jge key_done       ; ← "jge" отброшен → бесконечный цикл
```

Дизассемблирование подтверждает: от каждой строки осталась только первая инструкция.
Практический результат — `kuznyechik_set_key` крутится вечно:

```
$ ./build/gost-test
Тест 1: Расширение ключа (RFC 7801 §5.4)... <зависание, убит по таймауту>

$ ./build/gost-server config/server.json
=== ГОСТ Прокси-Сервер ===
Address: 0.0.0.0:10443
<зависание; /proc/PID/stat: state=R, utime=210 тиков за 2 секунды>
```

**Сервер и клиент на HEAD зависают на 100% CPU при старте, ещё до открытия сокета.**
Именно этот код попал в собранные пакеты `debs/` и `rpmbuild/RPMS/`.

### 3.2. Ассемблерная реализация в рабочем каталоге — SIGSEGV

Код переписан по одной инструкции на строку (проблема 3.1 устранена), но:

```
Program received signal SIGSEGV
0x...d23 in kuznyechik_set_key.key_rounds ()
rcx 0x1   r10 0x7fffffffd9a0   r11 0xfffecd00
```

`kuznyechik_set_key` хранит счётчик групп `g` в `r10d`, а вызываемая из цикла
`kuznyechik_L_avx2` первым делом делает `mov r10, rdi` — затирает счётчик
указателем на стек. Дальше `imul r11d, 8` даёт мусорное смещение и чтение
за пределами таблицы констант.

Помимо этого в том же файле:

| Проблема | Место |
|---|---|
| `kuznyechik_S_avx2`, `kuznyechik_inv_S_avx2`, `kuznyechik_precompute_tables` — пустые заглушки (`ret`) | конец `.text` |
| S-подстановка через `vpshufb` по 256-байтной таблице — `pshufb` индексирует только младшими 4 битами, математически неверно (в комментариях кода это признано) | `enc_loop`, `dec_loop` |
| Нарушение SysV ABI: `rbx`, `r12`–`r15` затираются без сохранения | `set_key`, `encrypt_ecb`, `encrypt_ctr` |
| `kuznyechik_encrypt_ecb` никогда не пишет в `out` (шифрует `in` на месте) | `.ecb_loop` |
| `kuznyechik_encrypt_ctr`: счётчик затирается `encrypt_block` (шифрование in-place) → это не CTR; неполный последний блок не обрабатывается → запись до 15 байт за границу `out` | `.ctr_loop` |
| Это не AVX2: используются `xmm` (128 бит), ни одного `ymm`; заявленные в STEP_PROGRESS.md функции `*_256`, `*_parallel_avx2` в файле отсутствуют | весь файл |

### 3.3. Таблица S-box в рабочем каталоге испорчена

`git diff` показывает, что в рабочем каталоге таблицы `S`/`S_inv` в
`gost_cipher.c` переписаны в hex — и при этом повреждены:

```
== Прямой S-box проекта vs RFC 7801 ==
  несовпадающих байт : 122 / 256
  первый расходящийся индекс : 132
  это перестановка?  : НЕТ (дубликатов 30, отсутствующих значений 30)

== Обратный S-box ==
  несовпадающих байт : 150 / 256
  это перестановка?  : НЕТ (дубликатов 21, отсутствующих значений 21)

  S_inv(S(x)) != x для 203 из 256 значений
```

S-box перестал быть биекцией, то есть шифр перестал быть обратимым. Проверка на
векторах RFC 7801:

```
K3            : ПРОВАЛ (ожид. DB31485315694343228D6AEF8CC78C44, получено 9F6AC9C3...)
K10           : ПРОВАЛ
encrypt_block : ПРОВАЛ
decrypt_block : ПРОВАЛ
roundtrip     : ПРОВАЛ   ← дешифрование не восстанавливает открытый текст
CTR roundtrip : OK       ← проходит только потому, что CTR в обе стороны шифрует
```

На HEAD та же таблица была **корректной**. Это регрессия, внесённая
незакоммиченными правками.

### 3.4. Что работает: C-реализация с HEAD

```
K3  : OK      encrypt_block : OK      roundtrip     : OK
K10 : OK      decrypt_block : OK      CTR roundtrip : OK
```

Полное соответствие RFC 7801. Это единственная пригодная к использованию
криптографическая основа в проекте.

## 4. Функциональное тестирование (end-to-end)

Чтобы проверить сетевую часть отдельно от сломанной криптографии, я собрал
отладочную копию в `/tmp/gp-fix`, где ассемблерный модуль заменён корректной
C-реализацией с HEAD (крипто-тесты в этой сборке проходят все 5 из 5).
Схема стенда: `curl → SOCKS5 (gost-client) → UDP → gost-server → HTTP на 127.0.0.1:8088`.

### 4.1. Туннель данные не передаёт

```
$ curl -sv --socks5 127.0.0.1:1081 http://127.0.0.1:8088/test.txt
* cannot complete SOCKS5 connection to 127.0.0.1. (5)
```

В логе сервера пакет виден, но обработчик молча выходит — нет ни строки `CONNECT`,
ни сообщения об ошибке:

```
22:16:46 [DEBUG] handle_packet: type=1  → HANDSHAKE response sent=1433
22:17:11 [DEBUG] handle_packet: type=2  ← DATA принят и молча отброшен
```

### 4.2. Причина №1: рассогласование порядка байт в session_id

```
сервер выдал  session_id = 7749363893351949254   (0x643c986966334873)
клиент запомнил session_id = 8306946027636145252 (0x7348336669983c64)
bswap(серверного) == клиентскому : True
```

`quic_layer.c:85` копирует `session_id` из ответа **в сетевом порядке байт**:

```c
memcpy(qc->session_id, &r->session_id, 8);   /* байты BE */
```

а `client.c:79` интерпретирует их как значение в хостовом порядке. Дальше клиент
делает `htonll()` ещё раз, сервер — `ntohll()`, и `find_session()` ищет
перевёрнутый идентификатор. **Ни один DATA-пакет не может быть сопоставлен с
сессией.** Тот же байт-своп затрагивает `nonce` (он выводится из `session_id`),
поэтому даже при исправлении поиска гамма у сторон разошлась бы.

### 4.3. Причина №2: перестановка payload необратима

`apply_permutation` (`session.c:406`) и `inverse_permutation` (`session.c:417`)
реализуют разные, не взаимно обратные операции. Более того, `apply_permutation`
уничтожает данные: индекс источника зависит только от `i % 4`, поэтому на выходе
получается повторяющийся 4-байтовый узор.

```
исходные данные : ABCDEFGHIJKLMNOPQRSTUVWXYZABCDEF
после apply     : CADBCADBCADBCADBCADBCADBCADBCADB
после inverse   : ABCD............................
восстановлено?  : НЕТ — данные потеряны безвозвратно
```

Это второй независимый блокер: даже с исправленным `session_id` полезная
нагрузка не восстановится.

### 4.4. Причина №3: демультиплексирование отсутствует

Все SOCKS5-соединения используют **один** UDP-сокет, и каждый поток
`proxy_data_thread` независимо вызывает `quic_client_recv()` на нём. Пакет,
прочитанный «не тем» потоком, просто выбрасывается:

```c
if (pkt_conn_id != expect_conn_id) return -1;   /* socks5.c:112 — пакет потерян */
```

При двух и более параллельных соединениях (то есть при любой реальной работе
браузера) данные теряются гонкой. Нужен один поток-читатель с очередями по
`conn_id`.

### 4.5. Причина №4: несовпадение формата CONNECT в proxy.c

`proxy.c` — третья, параллельная реализация клиента. Её формат запроса
несовместим с тем, что разбирает `server.c`:

* `server.c:147` ожидает `[0]=0x01 (команда), [1]=тип адреса, [2..5]=IP, [6..7]=порт`;
* `proxy.c:171` кладёт тип адреса в `[0]`, а IP в `[1..4]`;
* выбор «IP или домен» делается через `strchr(host, '.')` — любое доменное имя
  содержит точку и попадает в ветку IPv4, где `inet_pton` тихо не срабатывает и
  отправляются нули;
* в ветке IPv4 порт пишется в `connect_data[3..4]`, затирая последний байт адреса.

## 5. Безопасность

### 5.1. Handshake не аутентифицируется (критично)

`protocol_verify_handshake()` проверяет только `magic` и `type` — поле `auth_tag`
не проверяется вообще, и сам сервер эту функцию не вызывает
(`server.c:200` создаёт сессию сразу).

Проверка: отправляю UDP-датаграмму, состоящую из магии, типа `0x01` и нулей,
без знания ключа:

```
Сервер ОТВЕТИЛ на handshake без знания ключа.
  длина ответа : 1433
  выдан session_id : 7749363893351949254
Сервер принял усечённый 10-байтовый пакет и ответил, длина: 1433
```

Сервер — открытый релей для любого, кто знает порт. Также он принимает пакеты
длиной от 10 байт, но читает их как полную структуру `gost_packet_t` (1433 байта),
работая с неинициализированной памятью (`server.c:193`).

### 5.2. Воспроизводимое повторное использование гаммы (критично)

`session_id` генерируется через `rand()` **без `srand()`**
(`server.c:201`, `quic_layer.c:47`), а затем напрямую становится CTR-nonce
(`server.c:70`, `client.c:83`). Три независимых перезапуска сервера:

```
запуск сервера №1: session_id=7749363893351949254
запуск сервера №2: session_id=7749363893351949254
запуск сервера №3: session_id=7749363893351949254
```

При неизменном предустановленном ключе это означает **одинаковую пару
(ключ, nonce) при каждом старте сервера**. XOR двух перехваченных сессий
раскрывает открытый текст.

Повторное использование гаммы есть и внутри одной сессии: счётчики
per-connection во всех потоках инициализируются одинаково
(`socks5.c:130-131`, `222`, `229`; `server.c:174`), поэтому разные `conn_id`
шифруются одной и той же гаммой. Вдобавок `protocol_unpack_data:353`
присваивает `*counter = pkt_counter`, то есть счётчик отправки управляется
извне — тем, кто прислал пакет.

### 5.3. MAC подделывается тривиально (критично)

`compute_mac()` (`session.c:172`) складывает все 16-байтные блоки payload по XOR
и шифрует результат одним блоком. Такая конструкция инвариантна к перестановке
блоков и к парным инверсиям битов:

```
MAC оригинала                          : D63F84A020CB916E3EB2DA3FD04559DE
MAC после обмена двух блоков местами   : D63F84A020CB916E3EB2DA3FD04559DE
MAC совпал (подделка проходит)         : ДА
MAC после парной инверсии бита         : ДА
```

Так как режим — CTR, инверсия бита шифртекста напрямую инвертирует
соответствующий бит открытого текста. Атакующий может произвольно
модифицировать содержимое туннеля, сохраняя корректный MAC. Нужен настоящий
MAC (например, CMAC/HMAC на отдельном ключе), привязанный к длине и заголовку.

### 5.4. Отказ в обслуживании 256 пакетами (критично)

`create_session()` (`server.c:65`) перебирает слоты начиная с `free_slot_next`,
который только растёт и никогда не сбрасывается; освобождённые сессии не
переиспользуются, тайм-аута сессий нет (параметр `session_timeout` в конфиге не
используется).

```
успешных handshake: 256 из 300; первый отказ на попытке #256
max_sessions в конфиге: 256
```

256 неаутентифицированных UDP-датаграмм навсегда выводят сервер из строя
до перезапуска.

### 5.5. CPS (Chaffing/Pretense System) не даёт защиты

* ключ «CPS» захардкожен: `cps_key[i] = i * 0xAA` (`session.c:615, 647`);
* `protocol_make_cps_challenge` кладёт в `challenge_out` и `answer_out` **одно и
  то же значение** и отправляет и challenge, и ответ в одном пакете — проверять
  нечего;
* `protocol_verify_cps_challenge` сравнивает 32 байта, но шифрует блочной
  функцией только первые 16.

На стенде обмен всё равно не состоялся: `CPS: no response received`.

### 5.6. Утечка DNS и отсутствие IPv6

`socks5.c:206` резолвит имя **на стороне клиента** через `gethostbyname()` и
всегда отправляет серверу адрес типа `0x01` (IPv4). Это сводит на нет
`--socks5-hostname` (DNS-запросы уходят в открытый канал) и полностью исключает
IPv6. Дополнительно `gethostbyname()` не потокобезопасен, а вызывается из
множества потоков.

### 5.7. Эксплуатация и упаковка

* systemd-юниты в `rpmbuild/SPECS/gost-proxy.spec:70,86` не содержат `User=`,
  ни одной директивы усиления — сервер и клиент работают **от root**;
* один и тот же ключ по умолчанию
  `0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF`
  зашит во все конфиги (`config/*.json`, `etc/server.json`) и ставится с правами
  `0644`, то есть читаем любым пользователем системы;
* установленный в системе сервис находится в цикле аварийных перезапусков:

```
gost-proxy-client.service: Scheduled restart job, restart counter is at 3120
gost-client[245346]: Ошибка handshake
```

## 6. Прочие дефекты

### Сервер (`src/core/server.c`)

| Строка | Проблема |
|---|---|
| 198–247 | `sessions_lock` удерживается на всё время `handle_data_packet`, включая блокирующие `getaddrinfo()` и `connect()` с тайм-аутом 5 с. Единственный принимающий поток встаёт на каждом CONNECT — обработка полностью последовательная. |
| 54–56 | Хеш сессий — массив прямого отображения без цепочек. `session_hash_add` затирает коллизию: при совпадении `sid % 512` предыдущая сессия становится недостижимой, оставаясь `active` (утечка слота). |
| 105 | `find_session()` вызывается из `tcp_to_udp_thread` **без** `sessions_lock` — гонка. |
| 185–190 | Указатель на `proxy_conn_t` используется после освобождения `proxy_lock`; слот может быть переиспользован другим потоком. |
| 89–97 | На каждое TCP-соединение создаётся **новый** UDP-сокет, ответы уходят клиенту с чужого исходного порта — не пройдут NAT и `connect()`-нутый сокет. |
| 147 | Управляющие сообщения смешаны с данными: любые проксируемые данные, начинающиеся с `0x01` и длиной ≥ 8, интерпретируются как новый CONNECT. |
| 271–273 | Ключ разбирается через `sscanf("%2x")` без проверки длины и валидности hex; при коротком ключе остаток молча остаётся нулями. |

### SOCKS5 (`src/network/socks5.c`)

| Строка | Проблема |
|---|---|
| 188–191 | Нет проверки `n >= 5 + dlen + 2` перед чтением `buf[5+dlen]` — чтение неинициализированного стека. То же для ветки IPv4 (`buf[8]`, `buf[9]` при проверенном лишь `n >= 4`). |
| 171, 175 | Предполагается, что приветствие и запрос SOCKS5 приходят целиком за один `recv()`; частичное чтение не обрабатывается. |
| 63–73 | `dns_cache_store` пишет строго в свой бакет, а `dns_cache_lookup` использует линейное пробирование — записи теряются при коллизии. |
| 44–58 | При промахе `lookup` всегда обходит все 256 записей (`continue` вместо выхода). |
| 133–160 | Активный опрос: `poll` 100 мс → `tunnel_recv` 50 мс → цикл добора 10 мс. Постоянная нагрузка на CPU и задержки; пока поток ждёт в `tunnel_recv`, он поглощает и выбрасывает чужие пакеты. |
| 79, 289 | `shared_counter` присваивается и нигде не используется. |
| 242–245 | Результат `malloc` и `pthread_create` не проверяется. |

### Ассемблерные хелперы (`src/core/tcp_helpers.asm`)

* `tcp_write_all` обрабатывает только `EINTR`; `EAGAIN` (11) трактуется как
  фатальная ошибка — при срабатывании `SO_SNDTIMEO` (5 с, выставлен в
  `connect_to_target`) соединение будет разорвано вместо повтора;
* при `write() == 0` управление уходит в `.retry → .write_loop` без задержки —
  холостой цикл на 100% CPU;
* буфер `hex_buf` в `.bss` объявлен, но не используется (реально пишется стек).

### Протокол (`src/core/session.c`)

* `prng_state` — глобальное состояние без синхронизации, `prng_seed`/`prng_next`
  вызываются из всех потоков;
* `protocol_generate_header_seed` на каждом вызове перезаписывает `static
  zero_key` (гонка) и генерирует seed повторением одного и того же 16-байтного
  блока;
* padding вычисляется только из `session_id`, то есть постоянен на всю сессию —
  заявленная «случайность» отсутствует;
* `protocol_insert_padding`: массив `junk[]` заполняется и не используется;
  `memmove(payload + left + *data_len, payload + left, *data_len - left)`
  сдвигает не тот диапазон;
* `protocol_remove_padding` не вызывается из `protocol_unpack_data` — мёртвый код
  с иной логикой, чем у распаковки;
* `protocol_unpack_data:350` при `total_len == MAX_PAYLOAD - 4` читает 4 байта за
  границей буфера `decrypted`;
* размер выходного буфера в `protocol_unpack_data` не передаётся и не проверяется.

### Документация

* `README.md`: «HTTP работает стабильно» — не воспроизводится, туннель не
  передаёт данные ни по HTTP, ни по HTTPS; проблема не в GnuTLS;
* `STEP_PROGRESS.md`: «kuznyechik.asm переписан с SSE2 на AVX2», перечислены
  функции `kuznyechik_S_256`, `kuznyechik_encrypt_ctr_256`,
  `kuznyechik_encrypt_block_parallel_avx2` — в файле их нет, регистры `ymm` не
  используются, а `kuznyechik_precompute_tables` — заглушка `ret`;
* `README.md` описывает пакет как `[magic|type|conn_id|session_id|payload|auth_tag]`
  — это соответствует коду, но заявленный «auth-tag (encrypt-then-MAC) для
  проверки целостности» не обеспечивает целостности (п. 5.3).

## 7. Рекомендации по приоритетам

**Шаг 0 — вернуть сборку и корректную криптографию.**
Убрать `kuznyechik.asm` из сборки целиком и экспортировать проверенную
C-реализацию с HEAD как публичный API (`kuznyechik_set_key`,
`encrypt_block`, `decrypt_block`, `encrypt_ctr`, `encrypt_ecb`). Восстановить
таблицу S-box из HEAD. Это даёт зелёные тесты RFC 7801 за один коммит
(проверено в `/tmp/gp-fix`). К ассемблерной оптимизации возвращаться только
после того, как появится корректный эталон и тесты, сравнивающие ASM с C
на случайных векторах.

**Шаг 1 — блокеры передачи данных.**
1. Исправить порядок байт `session_id` (`quic_layer.c:85` ↔ `client.c:79`) —
   хранить в хостовом порядке, конвертировать только на проводе.
2. Убрать `apply_permutation` / `inverse_permutation` из тракта данных: сейчас
   они уничтожают payload и не дают ничего в плане маскировки.
3. Сделать демультиплексор: один поток читает UDP-сокет и раскладывает пакеты
   по очередям `conn_id`; рабочие потоки читают из своих очередей.
4. Либо привести `proxy.c` к формату `server.c`, либо удалить его — сейчас это
   третья несовместимая реализация клиента.

**Шаг 2 — безопасность (до любого использования вне лаборатории).**
1. Аутентифицировать handshake: проверять `auth_tag` в
   `protocol_verify_handshake` и вызывать её из `server.c`.
2. Заменить `compute_mac` на CMAC/HMAC на отдельном ключе, с привязкой длины и
   заголовка; сравнение — за постоянное время.
3. Nonce брать из `getrandom()`, а не из `rand()`; сделать nonce уникальным по
   паре (сессия, направление, conn_id) и запретить приём счётчика из пакета
   (окно антиреплея вместо `*counter = pkt_counter`).
4. Переиспользовать слоты сессий, добавить `session_timeout` и ограничение
   скорости на handshake (`rate_limit` в конфиге уже есть, но не используется).
5. Резолвить имена на сервере (поддержать тип адреса `0x03` в клиенте),
   добавить IPv6.
6. В systemd-юнитах задать `User=`, `NoNewPrivileges=`,
   `ProtectSystem=strict`; конфиг с ключом — `0600`; генерировать ключ в
   `%post` вместо публикации константы.

**Шаг 3 — производительность и корректность сервера.**
Вынести `connect()`/`getaddrinfo()` из-под `sessions_lock`, добавить цепочки в
хеш сессий, убрать создание UDP-сокета на каждое соединение, заменить активный
опрос на событийную модель, поправить обработку `EAGAIN` в `tcp_write_all`.
